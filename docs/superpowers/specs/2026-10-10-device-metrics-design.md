# amqe: network snapshot variant

Read-only design for Doctor Biz, October 10, 2026. No source edits, builds, hardware/network access, service starts or issue changes. The brainstorming skill informed this design; implementation and transport selection remain with the parent. The existing finish-all authorization permits this investigation without another approval stop.

## Recommendation and tradeoff

For routine operation, poll a small cached numeric firmware snapshot over the existing control HTTP server, then export Prometheus on the host. This avoids permanent USB ownership and serial-open resets. UART remains stronger evidence when Wi-Fi fails: network telemetry cannot independently distinguish an unreachable board from a failed network path. Retain sole-owner UART during controlled acceptance; do not treat HTTP silence as capture failure. New HTTP polling also consumes device network/httpd resources, so live overhead acceptance remains necessary.

`GET /api/metrics` is a **proposed new route**, not an existing endpoint. Keep `/api/state` unchanged: `web.rs:63` and `core/src/store.rs:StateView` expose only recognition state, level, settings flag and private song/history data. None is a pipeline-health API, and the level measurement Instant is not serialized. Do not use its body for metrics.

## Existing lifecycle and ownership

`lib.rs:run` initializes listener/encoder telemetry queues before starting capture because the first ESP-IDF std mutex access allocates. It then starts the existing metrics owner, network, streaming, Sonos and `web::start`. Keep that order: initialize/touch one additional static cache mutex beside the existing queue initialization, before producers run. Its static lifetime serves both metrics and the server closures; no new task, channel, Arc allocation or capture argument is necessary. `web::start` already keeps an `EspHttpServer<'static>` alive and handles responses in its 10 KiB HTTP task.

`audio_in.rs:metrics` runs on core 1, priority 3, 6 KiB stack and a 100 ms loop. Capture runs on core 0, priority 24; supervisor core 1 priority 11. Capture/encoder observations are logged about every ten seconds; listener/encoder queues each drain at most two records per metrics iteration. Use those same captured values and dequeued records, never another queue consumer, scan or ring lock. No cache writes from capture, encoder, ISR, network callback or listener cleanup.

At `log_capture`, create a small numeric capture value from **the local values already read for logging**; capture its original begin/end times. At `render_encoder_event`, copy a numeric subset of a dequeued Window/Boundary before rendering it. Keep feature-gated probe arrays, errors and private identities out. Update the cache outside all source/queue locks; keep logging outside its lock. Preserve existing swaps/resets exactly once: never re-read swap-based maxima to populate HTTP.

## Synchronization

Use a fixed-size `Copy` snapshot inside a separate `Mutex`. Publisher builds each family locally, uses `try_lock`, copies that family and releases; contention skips a refresh and naturally ages that family's last timestamp. HTTP uses `try_lock`, copies the snapshot immediately and releases before JSON serialization or socket I/O. Return a bounded HTTP 503 on unavailable/poisoned cache rather than waiting, panicking or serving invented zeros. Requests never hold two locks at once. No formatted string, heap query, allocation, task query or log statement occurs inside the cache guard.

A blocking Mutex would keep capture safe directly, but allows slow HTTP work to delay the metrics owner if the guard accidentally spans formatting. The `try_lock`/copy contract makes that failure bounded. Atomics for every field would avoid a lock but would require a consistency protocol across timestamps/counters, especially u64 on this target; that is unnecessary here. Reusing capture atomics directly in HTTP would duplicate sampling and mix times while failing to cover the non-atomic dequeued windows.

Use an explicit unavailable `Option`/validity tag for each family. A startup snapshot is valid JSON with absent observations, never zero-valued healthy measurements. All serialized strings are fixed enum values or fixed schema field names. `serde_json` already exists; JSON body allocation follows the current web convention. Encode after releasing the lock, with an explicit response-size ceiling; use a bounded writer or fixed capacity serialization buffer rather than a body that can grow with requests. Do not stringify the whole source record.

## Proposed numeric schema and cost

Version 1: `schema_version`, `served_device_us`, optional capture, optional encoder, optional telemetry-loss summaries. `served_device_us` is read once using the existing device timer convention at HTTP response creation; family timestamps describe acquisition, not request receipt. Proposed fields, not implemented names:

| Family | Existing authoritative values to copy |
| --- | --- |
| capture | capture_begin_us, capture_end_us; frames, callbacks, queue_overflows, software_dropped_frames, read_errors, restarts, supervisor_restarts, overflow_restarts, settling_discarded_frames, discontinuities, health_restart_requests; read_service_delay_estimate_max_us, raw_work_max_us, meter_work_max_us, store_work_max_us, raw_read_max_us; internal_free/internal_largest/internal_min_sum and PSRAM equivalents |
| encoder | window_start_us/window_end_us, telemetry_epoch/window; encoded_frames, resets, block_samples, listeners_start/end, encode_max_us, stack_free_bytes; raw_read_frames/overruns/retries; encode_wall_total_us, raw_wait_total_us/max_us, encoded_lock_wait_wall_total_us, encoded_push_held_wall_total_us; task_runtime_us plus runtime_valid |
| loss | existing listener/encoder queue dropped counts and loss_occurred flags, with metrics-owner observation timestamp; optionally metrics_stack_free_bytes from the existing export query, not a second scan |

Times are microseconds on device, memory bytes, frames explicitly PCM frames versus codec frames. Encoder values are **window gauges**, never since-boot totals. `frames` increments immediately after I2S reads and before drops/settling/publication (`audio_in.rs:267`), so name its host series read frames, not published frames. u32 source counters wrap. Runtime includes charged interrupts; raw_read_max_us measures encoder raw-ring copying. Heap minimum sums combine independent region lows, largest blocks are snapshots. Preserve those qualifiers in descriptions. Encoder startup/boundary stack zero means unscanned; only export measured window headroom.

RAM budget proposal: about 32 capture scalar slots, 24 encoder scalar slots and 8 loss/header slots, represented conservatively as 64-bit slots, total 512 bytes plus validity/alignment/mutex. Require target `size_of` verification with a hard cap **<=768 bytes static cache**, <=768-byte HTTP/local copy and **<=4096-byte serialized response**. These are proposed limits, not measured target sizes. Avoid holding an extra entire encoder Window (which can include probe arrays) on the 4 KiB metrics stack. A bounded serialization buffer adds up to 4 KiB transient storage; select heap rather than placing it on the HTTP stack, and measure actual heap/stack overhead. Reserve once only if lifecycle ownership is clear; do not add a new shared serializer lock to save one allocation.

First unit excludes listener-session details: current receipts are emitted on departure and expose peers, not live lag. A later fixed two-slot lifecycle mapping would need authoritative stable session identity that is absent today. Do not hash a peer into a supposedly safe identity or mislabel a final write maximum as live health.

## Identity, settings and freshness limits

There is no existing durable device ID, boot nonce or build revision in the state API/source boot path inspected. `CONFIG.hostname` is configurable and not guaranteed unique; host uses a short configured alias. Encoder telemetry epoch/window resets with process lifetime and changes during codec/reset events: it is not boot identity. `served_device_us` regression detects many resets but **cannot prove continuity** when a reboot plus scrape outage produces a larger next uptime. No rates or wraps across an outage may assume the same boot. Until boot identity is added as explicit metadata, mark continuity unknown and restrict rates to bounded consecutive observations; do not claim amqe's complete identity acceptance.

A future once-per-boot random nonce would solve that gap without a stage counter or I2S work, but requires verifying the pinned platform entropy API and initialization point before code. No API name is asserted here. Even consecutive polls cannot strictly rule out a fast reset. Recommendation: retain raw count gauges and existing encoder-window rates, but suppress host-derived capture counter rates until a verified boot token exists; any exploratory rates need an explicit inferred-continuity qualification. A build revision also needs an explicit reproducible build input; package version/operator-supplied revision does not attest flashed bytes. Keep these unavailable rather than inventing them.

`sonos::Snapshot` has active_format and config; `Handle::snapshot` takes its status mutex and refreshes active format. Do not call it under the metrics/cache lock or dump its config. Effective codec/buffer metadata should be a separate tiny allowlisted read added only after checking its nested lock cost and whether the preset describes the current listener or next Play. Recognition enable/PGA are build config values (`config.rs`) but Wi-Fi password/SSID and MQTT URL share that struct: never serialize Config. No workload/input provenance exists in the device; matched revision experiments need a separate host receipt.

Keep family acquisition timestamps unchanged on successful HTTP responses. Host computes device acquisition age from served_device_us minus sample-end timestamp, tracks monotonic host time since last successful validated response, and requires both freshness gates. Proposed stale gate 30 s for ten-second families. Non-advancing timestamps, request timeout, malformed/oversized body, future timestamp or missing family means unavailable; clear source series on expiry while retaining freshness/status series. Queue loss invalidates completeness. A fresh response can contain stale observations.

Absent and explicitly unavailable: publication head/generation, encoded frame age, live per-listener lag/write measurements, Wi-Fi/IP generations and authoritative cumulative disconnect totals, full live task-stack set, boot/build attestation. Do not add fabricated zero panels. Wi-Fi disconnect text has both callback and supervisor messages and is unsuitable for exact double-count-free totals.

## Host and Grafana

Use existing uv Python project and stdlib bounded JSON HTTP client plus loopback Prometheus exporter. One configured device, one in-flight request, no redirects, proxies disabled as current harnesses do, explicit timeout and response-size limit. Proposed five-second polling reads the same ten-second cached samples; HTTP request frequency is not source sampling frequency. Fixed metric allowlist/enum labels only; no peer/MAC/IP/SSID/song/error text, nonce/epoch/window or build hash as labels. Convert device microseconds to seconds for Prometheus. Serve numeric cache only; no UART/private audio endpoint.

No credentials, authentication policy, exposed listen addresses or deployment changes are selected here. Review the LAN trust boundary before implementation of a new numeric route; a host alias is not authentication. Existing `.agent/grafana` remains agent telemetry. Reuse its datasource/provider with a separate device dashboard/job after pinned version and actual Linux connectivity review; its current wildcard bindings/default password/mutable images are not deployment acceptance.

## First unit and acceptance

Small first unit: host-testable Rust numeric snapshot/cache module, initialization in lib.rs, reuse of capture local values and dequeued encoder records, and proposed GET route. Approximate 180–260 Rust LOC plus 160–220 test LOC; host poll/export adapter then about 180–250 Python LOC plus tests. No source instrumentation beyond copying existing observations. Parent owns overlapping audio_in.rs/stream.rs/lib.rs/web.rs edits and integration with its admission work.

TDD: absent-at-start JSON; exact independent field/unit expectations; source timestamps preserved across repeated GETs; bounded cache/body sizes; contention/poison return unavailable without blocking; invalid runtime/stack sample stays absent; loss receipt retained; capture read count never renamed publication count. Real local HTTP/file-independent host integration covers body ceiling, timeout, no redirects, malformed and stale responses. Run the repo's canonical `scripts/check`, which includes host and target validation; do not invent a separate abbreviated release gate. Then parent-owned live acceptance compares the same image with collector off/on under matched workload/input, measures capture/encoder/heap/stack overhead and verifies a known existing controlled event from source through scrape to panel. Demonstrate stale data after stopping input/polling independently, and HTTP request saturation boundedness. Until live tests and missing identity/stage work pass, this is partial amqe implementation, not closure.
