## What the lab is

z5fs asks for a dedicated runner, a dedicated board, a controlled audio
source, a configurable AP and an exclusive reservation, with bounded
flash/collect/restore and machine-readable artifacts. Mapped to this desk:

| Need | Reality on 2026-10-15 |
|---|---|
| Runner | This workstation, registered as a self-hosted runner, label `esp-hil` |
| Board | The ESP32-A1S on `/dev/ttyUSB0` is the dev board; it may be flashed, rebooted and broken freely |
| Audio | Workstation headphone jack → board LINE IN, connected since Oct 8 |
| AP | UniFi. Client block/kick and per-client bandwidth rules through the controller; `tcpdump` over SSH on the AP; client stats for channel/RSSI/retries |
| Reservation | The runner runs one job at a time; a `flock` on `/dev/ttyUSB0`'s lock file covers manual runs from a shell |
| Automation | `scripts/flash`, the harness receipts and the probe restore pattern, wrapped in one job script |
| Schedules | per-PR: two-listener churn; nightly: reconnect, churn, recovery; weekly: soaks |

The Sonos stays a shared household device: every HIL job that touches it
preconditions on remote STOPPED and an ungrouped coordinator, and most
jobs do not touch it at all.

## Security

Self-hosted runners execute workflow code with the runner user's rights.
The repo is private and only Doctor Biz pushes, so PR workflows from
forks are not a concern today; the runner is registered to this repo
only, not the org, and `workflow_dispatch`/`schedule` jobs are the only
ones that target `esp-hil` until the lab has proven itself. UniFi and AP
credentials live outside the repo (an ignored `hil/credentials.toml`,
same rule as `firmware/cfg.toml`) and reach jobs as runner-local files,
never as repo contents or workflow text.

## Tasks

1. **Runner.** Pinned `actions/runner` release, checksum verified, in
   `~/actions-runner`; `config.sh --unattended --labels esp-hil`;
   `systemd --user` unit with linger so it survives logout; `gh api
   repos/…/actions/runners` shows it online. No sudo.
2. **Board lock.** `scripts/with-board`: `flock` on
   `$XDG_RUNTIME_DIR/esp-hil.lock` (fallback `/tmp`), bounded wait,
   runs the wrapped command; the flash, probe and churn scripts use it.
   Test with two concurrent invocations.
3. **UniFi access.** Read-only first: list clients, find the board's
   MAC (`70:4b:ca:87:18:3c`), record channel/RSSI/retries. Then, with
   the dev board only: block for N seconds and unblock; set and clear a
   bandwidth limit; verify each from the board's own network generation
   and listener telemetry. Capture: `tcpdump` on the AP over SSH for one
   null-control batch. API shapes verified at implementation against the
   controller, not assumed.
4. **First HIL workflow.** `hil-churn.yml`, `workflow_dispatch` only,
   `runs-on: [self-hosted, esp-hil]`: flash the ordinary image, run
   `scripts/listener-churn --cycles 10`, upload the receipt, restore.
   Green once by hand before any schedule.
5. **Per-PR and schedules.** Two-listener churn on PRs that touch
   `core/`, `firmware/` or `scripts/`; nightly reconnect (UniFi kick)
   and churn; weekly `stream-soak`. Each job restores the ordinary image
   and leaves settings unchanged.
6. **Tickets.** z5fs closes on 1–4 green; n4jb and ek5b get their AP-side
   evidence from Task 3; 97bk unblocks.

## Limits

UniFi client block is a controller action, not RF loss; it exercises
the board's reconnect path, not interference. Per-client bandwidth rules
shape at the AP, not at the receiver. Both are recorded as what they are.
